# InternHub Supabase Schema

`schema.sql` is a complete, from-scratch rebuild of the database for the
InternHub multi-tenant SaaS platform. It was generated by reading every
`.from("...")` call, Zod validation schema, and TypeScript type in this
repo, so the column names match what the app actually sends/expects.

## How to apply

1. Open your Supabase project → **SQL Editor**.
2. Paste the entire contents of `schema.sql` and run it. It is safe to
   re-run: Phase 0 drops every table/view in `public` first.
3. Create your first account through the app's `/register` flow (or in
   Supabase Auth directly), then run:
   ```sql
   UPDATE public.profiles SET role = 'super_admin', status = 'active'
   WHERE user_id = (SELECT id FROM auth.users WHERE email = 'you@example.com');
   ```
4. From the Super Admin dashboard you can now create universities; each
   university admin then manages their own departments, programs,
   students, companies and evaluation rules — nobody touches another
   tenant's data because every table is isolated by `university_id` +
   Row Level Security.

This was tested end-to-end against a local PostgreSQL 16 instance
(tables, triggers, RLS policies, and a full signup → university →
student → company → internship → application → placement → weekly log
→ attendance → evaluation flow all verified to run without errors)
before being committed.

## What was fixed vs. the previous script

The previous schema you were using had several mismatches against the
actual Next.js code, which is why it "had a lot of issues":

| Problem | Fix |
|---|---|
| Code used both `companies` and `host_organizations` for the same entity | Single `companies` table + an updatable `host_organizations` view |
| Some dashboard pages queried `applications`, API routes used `internship_applications` | Single `internship_applications` table + an updatable `applications` view |
| `companies.status` (text) and `companies.is_active`/`is_verified` (bool) were both queried by different routes | Both kept, and a trigger keeps them in sync |
| `supervisors`, `external_evaluators`, `licenses`, `settings`, `messages`, `company_users`, `audit_logs` were used throughout the app's API routes but never existed in the DB | All created with the exact columns those routes read/write |
| `profiles` had no `first_name`/`last_name`, but relational joins like `profiles:user_id(first_name,last_name)` depend on them | Added |
| Status enums didn't match `src/lib/validations.ts` (e.g. old `application_status` was `applied/university_approved/...`, code actually uses `pending/under_review/approved/rejected/withdrawn`) | Every status/enum now matches the Zod schemas exactly |

## Known app-code issues this SQL script cannot fix on its own

These are bugs in the **frontend/API code**, not the database — flagging
them so you can fix them separately:

- `src/app/(dashboard)/student/page.tsx`, `company-hr/page.tsx`,
  `university-admin/page.tsx`, `department-coordinator/page.tsx`, and
  `student/applications/page.tsx` filter with
  `.eq("student_id", user.id)` — but `student_id` on
  `internship_applications` is the `students.id` (a separate row), not
  the Supabase auth user id. These queries should first look up
  `students.id` via `user_id = auth.uid()`, then filter on that.
- `src/app/api/internships/route.ts` checks `companyCheck.data.status`
  for `"suspended"` — this now works since `status` exists, but make
  sure any place that *writes* company status writes to `is_active`
  too (the DB trigger keeps them in sync either direction, so writing
  either column is safe).
